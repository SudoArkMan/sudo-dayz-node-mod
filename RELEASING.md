# Releasing

The checklist for cutting a release. It is written to be worked through in
order, and the two decision points near the top have to be settled before the
first release rather than during it.

## Decisions to settle before the first release

These are not steps. They are questions with consequences, and they are here so
the answer gets recorded rather than assumed.

### 1. Which version number

The code now carries the version in one place only. Two things still disagree
with it:

| Where | Says |
| --- | --- |
| `CMakeLists.txt` line 7, `project(... VERSION ...)` | `0.1.0` |
| `resources/brand/splash/sudo-splash-760x440.png` | `BUILD 0.4.1` |

Everything else is generated from the first of those. CMake configures
`src/version.h.in` into `version.h`, `main.cpp` hands `NODEMOD_VERSION` to
`QCoreApplication::setApplicationVersion`, and the window title, the About box,
the start page, the update check and the Windows file properties all read it
back from there. Bumping the `project()` line is the whole change.

The splash is artwork and is the author's to change. `CHANGELOG.md` is written
for `0.1.0`, matching the code. Whatever number is chosen, the splash and the
`CHANGELOG.md` heading both have to say it before the tag goes on.

`--version` on the built executable is what a bug report will quote, and it can
no longer drift from the build, because there is nowhere for it to drift to.

### 2. Whether `resources/catalog.json` ships

This is the open question, and it is deliberately not answered here.

**The facts.**

- `resources/catalog.json` is 2.9 MB and is generated by
  `tools/build-catalog.mjs`. The generator reproduces the currently committed
  file byte for byte, so the file and the rule it was built under can be
  checked against each other.
- Its source is an index of `P:/scripts`, which is Bohemia Interactive's
  Enforce Script source, unpacked from an installed copy of DayZ. It contains
  6,108 class names, 29,024 method signatures, 403 enums, 362 globals and 578
  constants taken from that source.
- Alongside names and signatures it carries **documentation comments lifted
  from Bohemia's own source**. Names and signatures are the kind of thing an
  API reference is made of; prose comments are authored text, and they are the
  part of the file that makes this a question rather than a formality.
- The repository is MIT licensed. Committing the file as it stands has this
  project purporting to license that derived content under MIT, which is not
  something this project can grant.
- The application needs the catalogue at startup. Without it the palette is
  empty and most of the tool does nothing. `main.cpp` takes `--catalog <path>`
  and defaults to `resources/catalog.json`.
- Bohemia Interactive's own terms for DayZ Tools and for modding are the
  document that governs this. They have not been read in preparing this
  checklist, and reading them is part of answering the question.

**The options, with what each one costs.**

| Option | What it means | Cost |
| --- | --- | --- |
| A. Ship as now | `catalog.json` stays committed and ships in the release | The redistribution question stays unanswered in public |
| B. Do not commit it | Ship the generator; the user builds the catalogue from their own DayZ installation | The index generator `build_index.mjs` is not in this repository, so option B needs it brought in first. Every user then needs DayZ Tools and a mounted `P:` |
| C. Ship it without the comments | Strip the documentation comments in the generator, keep names and signatures | Loses the inline documentation in the inspector. Needs a change in `tools/build-catalog.mjs` and a rebuild of the file |
| D. Ship as now, under its own terms | Keep the file, state in `THIRD-PARTY-NOTICES.md` that it is derived from Bohemia's source and is not covered by this project's MIT grant | Honest labelling, but does not by itself create permission |
| E. Ask | Put the question to Bohemia Interactive before the first release | Time, and an answer that may not come |

Whatever is chosen, the "Node catalogue" section of `THIRD-PARTY-NOTICES.md`
has to be rewritten to say so before publishing. That section currently says
the question is open.

### 3. What the release actually deploys

The deploy line in `CMakeLists.txt` now drops the three binaries that are not
Qt code and that this application never loads: `opengl32sw.dll`,
`D3Dcompiler_47.dll` and `dxcompiler.dll`. Measured against the release build,
that takes the deploy from 25 files and 93.6 MB to **22 files and 49.6 MB**,
and removes three sets of third party terms that would otherwise have to travel
in `packaging/licenses/`.

One thing is still open.

**`Qt6Pdf.dll` ships.** The line does not pass
`--skip-plugin-types imageformats`, so `imageformats/qpdf.dll` is deployed and
pulls `Qt6Pdf.dll` in behind it. Qt PDF comes from the `qtwebengine`
repository, which is not installed on this machine, so it is the one component
whose licence could not be read off disk. The application has no PDF code and
no image loading beyond the PNG artwork compiled into the binary.

| Option | What it means | Cost |
| --- | --- | --- |
| A. Add `--skip-plugin-types imageformats` | Removes `imageformats/` and `Qt6Pdf.dll`, about 8 MB, and closes the licence question | Qt then cannot decode GIF, ICO, JPEG or SVG from disk. Nothing in the application does that today, so the cost is a constraint on future code rather than a change in behaviour |
| B. Leave it and establish the licence | Nothing about the artifact changes | Qt PDF's licence has to be confirmed from a source other than this machine, and `THIRD-PARTY-NOTICES.md` updated to state it |

Whichever is chosen, `THIRD-PARTY-NOTICES.md` and
`packaging/licenses/README.txt` both describe the artifact and both have to
match it.

Also worth a deliberate look before the first release: `--no-opengl-sw` drops
the Mesa software OpenGL fallback. That is the one exclusion that can turn into
"it will not start" on a machine with no working OpenGL driver, which makes the
clean-machine start at the end of `tools/release.ps1` the check that matters.

### 4. One-time repository setup

- Add the repository's compare links to the bottom of `CHANGELOG.md` once the
  remote exists. They were left out rather than guessed at.
- Turn on private vulnerability reporting in the repository's Security
  settings. `SECURITY.md` tells reporters to use it.
- Confirm the contact address sudoarkman@gmail.com is one that is
  read, because `CODE_OF_CONDUCT.md` points at it.
- Confirm the update check in `src/update.cpp` names the real owner and
  repository. It asks
  `https://api.github.com/repos/<owner>/<repo>/releases?per_page=20`, so a
  wrong name gives every user "no update available" forever, and the first
  release is the only chance to notice before anyone has installed it.
- The update check reads release tags. Tag releases `v<version>` from the
  start, because changing the tag shape later strands every installed copy on
  the old one.

## Cutting a release

### Before building

1. Working tree is clean and on the release branch.
2. Version agreed, the `project()` line bumped, and the splash artwork and
   `CHANGELOG.md` heading agreeing with it, per decision 1 above.
3. `CHANGELOG.md` has an entry for this version with the real date, and the
   `[Unreleased]` section above it is empty.
4. `THIRD-PARTY-NOTICES.md` matches what this release actually ships. If the
   Qt version changed, or a deploy flag changed which DLLs go out, that file
   changes with it.

### Build and test

Close any running `DAYZSUDONodeMod.exe` first. A running application holds its
own binary, the link fails, Ninja stops before it relinks the test targets, and
every number after that is read off a stale binary.

```
cmake -S . -B build/release -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=C:/Qt/6.11.0/mingw_64 -DCMAKE_CXX_COMPILER=C:/Qt/Tools/mingw1310_64/bin/g++.exe
cmake --build build/release
```

Run all 19 suites and keep the output:

```
for f in build/release/tests/*.exe; do "$f" resources || echo "FAILED: $f"; done
```

The corpus suites need a DayZ installation and a mounted `P:` drive to mean
anything. A release should be cut on a machine that has both, so
`pbotest --all`, `modlibrarytest` and `importtest` run against the real corpus
rather than skipping.

Check by hand, because no suite covers it:

- `build/release/DAYZSUDONodeMod.exe --version` prints the agreed version.
- The application opens `resources/SUDO_Link.sdzn`, the palette is populated,
  and generating code produces a file.

### Deploy Qt

The application must stay dynamically linked to Qt. That is a licence
requirement and `THIRD-PARTY-NOTICES.md` explains it. Never configure a static
Qt for a release.

There is no deploy step to run by hand. `cmake --install` carries an install
rule that runs `windeployqt` itself, so a build that skips it cannot happen,
and `resources/` and the licence texts are installed by the same rules. The
staged folder and the ZIP are therefore the same folder, made the same way:

```
cmake --build build/release --target stage
cpack -G ZIP --config build/release/CPackConfig.cmake
```

The flags that rule passes are in `CMakeLists.txt`, and each one is load
bearing:

| Flag | Why |
| --- | --- |
| `--compiler-runtime` | a MinGW build needs libgcc and libstdc++ on a machine with no toolchain |
| `--no-translations` | the application has no translations of its own, so Qt's 32 message catalogues would localise its standard dialogs inside an otherwise English interface |
| `--no-opengl-sw` | drops `opengl32sw.dll`, 19.7 MB of Mesa software OpenGL |
| `--no-system-d3d-compiler` | drops `D3Dcompiler_47.dll`, 4.0 MB |
| `--no-system-dxc-compiler` | drops `dxcompiler.dll`, 20.4 MB |

The last three are not Qt code and this application loads none of them: it is a
Qt Widgets program with no `QOpenGLWidget`, no Qt Quick and no shader
compilation, and the canvas paints through the raster engine. Measured against
the release build, the line produces **22 files and 49.6 MB**, against 25 files
and 93.6 MB with the three left in.

**Do not skip the `tls` or `networkinformation` plugin types.** The update
check in `src/update.cpp` speaks HTTPS to `api.github.com`, and without
`tls/qschannelbackend.dll` the request fails at the handshake, which looks like
"there is no update" rather than like a broken build.

`--no-opengl-sw` is the one flag that needs a deliberate answer rather than a
default. `opengl32sw.dll` exists for machines with no working OpenGL driver,
and dropping it is the saving most worth having right up until it turns into
"it will not start on my machine" from a user with old graphics drivers.

Re-measure at release time and re-check `THIRD-PARTY-NOTICES.md` against what
actually lands in the staged folder. A Qt point release changes file sizes, and
a new `#include` can pull in a module nobody intended to ship.

**Start the packaged executable on a machine without Qt installed** before
publishing. That is the only check that the deploy is complete, and it catches
a missing platform plugin immediately. `tools/release.ps1` does this at the end
of its run by unpacking the ZIP with Qt taken out of `PATH`. While the
application is open, agree to the update check once and confirm it reaches
GitHub and reports a result, because a missing TLS backend fails silently.

### Licence files in the archive

Shipping the Qt DLLs is redistribution of Qt, so the archive needs the text.
Nothing here is copied by hand: `packaging/licenses/` is installed whole into
`licenses/` beside the executable, and `LICENSE` and `THIRD-PARTY-NOTICES.md`
are installed at the top of the folder. This is what the archive holds and what
each file is there for:

| In the archive | Covers |
| --- | --- |
| `LICENSE` | The project's own MIT terms |
| `THIRD-PARTY-NOTICES.md` | Everything that is not this project's code |
| `licenses/README.txt` | What each file below applies to |
| `licenses/Qt-LICENSE.txt` | Qt. A copy of `C:/Qt/Licenses/LICENSE`, which carries both the LGPLv3 and the GPLv3 it supplements |
| `licenses/GPLv3.txt` | The GPLv3, as the licence the GCC exception modifies |
| `licenses/GCC-Runtime-Library-Exception.txt` | `libgcc_s_seh-1.dll` and `libstdc++-6.dll` |
| `licenses/MinGW-w64-runtime-COPYING.txt` | The mingw-w64 runtime |
| `licenses/winpthreads-COPYING.txt` | `libwinpthread-1.dll` |
| `resources/mod-template/LICENSE.md` | Stays where it is. Travels inside every scaffolded mod |

Two things to check rather than assume:

- The Qt licence text must come out of the Qt install being shipped, so it
  matches the version. `packaging/licenses/Qt-LICENSE.txt` is currently
  byte for byte identical to `C:/Qt/Licenses/LICENSE`, and
  `packaging/licenses/GPLv3.txt` to
  `C:/Qt/6.11.0/Src/qtbase/LICENSES/GPL-3.0-only.txt`. Re-check both after a Qt
  upgrade.
- If the deploy line ever stops excluding `opengl32sw.dll`,
  `D3Dcompiler_47.dll` or `dxcompiler.dll`, their own terms have to be obtained
  and added to `packaging/licenses/`. None of the three is covered by anything
  in that folder today, which is correct only for as long as none of them
  ships.

The release notes must state, in words a reader will actually see:

> This application uses the Qt framework version 6.11.0 under the GNU Lesser
> General Public License version 3. Qt is dynamically linked and its libraries
> ship as separate files, which can be replaced. The Qt sources are available
> from https://download.qt.io. The full licence text is in the `licenses`
> folder.

### Publish

1. Tag: `v<version>`, annotated.
2. Create the GitHub release against that tag. Paste the `CHANGELOG.md` entry
   as the body, then the Qt notice above.
3. Attach the archive. Include the SHA-256 of the archive in the release body,
   because there is no code signing certificate and a checksum is the only
   thing a cautious user can check.
4. Attach the test suite output if the release is a first for a major feature.

### After

1. Add a fresh empty `[Unreleased]` section to `CHANGELOG.md`.
2. Download the published archive on a machine that is not the build machine,
   extract it, and run it. Do this before telling anyone the release exists.

## Things that are not automated, and why

There is no CI workflow in `.github/`. The suites that carry the interesting
numbers need a DayZ installation, 254 installed Workshop mods and a mounted
`P:` work drive, none of which exist on a hosted runner. A CI job that ran only
the suites which skip themselves would report green while checking almost
nothing, which is worse than no job at all. If CI is added later, it should say
plainly in its own name that it is the subset.

There is no installer and no code signing. The release is an archive.
